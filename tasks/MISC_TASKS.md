# Miscellaneous — open backlog

Open rows that belong to no skin-subsystem backlog. Read the owning skill before picking one up.

| ID | Item | Notes |
|---|---|---|
| M37 | EQ rules: map an EQ setting to a track, album or artist | A rule-based system that applies a saved EQ curve automatically when a matching track starts. **Add a rule:** a button on the EQ window opens a rule editor prefilled from the current track. The editor picks the scope (this track, this album, this artist, or a whole source), and the source the rule applies to: the current track's source (local, Plex, Jellyfin, Subsonic, Emby, radio) or all sources. A track rule also picks this version (the one file or server item) or all versions (every copy of the song: other albums, remasters, live takes, other formats). It saves the current band values plus preamp as the rule's curve. **View rules:** a menu item opens a list of every rule (scope, match, source, curve name) where rules can be edited, disabled or deleted. **Matching:** the most specific rule wins (track > album > artist > source); at the same scope, a rule for one source beats an all-sources rule, and a this-version track rule beats an all-versions one. When no rule matches, the existing behaviour applies: the AUTO genre preset if it is on, otherwise the last manual setting. A manual fader drag or preset click during playback overrides the rule for that track only. Open questions: how an all-sources rule matches the same track or album across sources (by artist/album/title, since IDs differ per server), how an all-versions rule recognises the same song (artist plus title with suffixes like "Remastered" or "Live" normalised away, or MusicBrainz recording ID when tagged), and whether a rule can point at a named preset as well as a raw curve. **Done when** rules can be added from the EQ button, are listed and editable from the menu, apply on track change in Classic, Original, `.wal` and `.wmz` EQ windows, and survive a relaunch. Skills: `audio-system` (EQ, AUTO genre preset), `app-state` (persistence), `user-guide` (menus). |
| M38 | Classic skin loads stop rewriting visualization settings | `WindowManager.applyClassicVisualizationDefaults` runs on every Classic launch and every Classic skin pick. It rewrites both windows' vis_classic profile to Purple Neon, turns fit-to-width back on in both, sets `spectrumQualityMode` back to vis_classic, and posts six live reload notifications. Classic skins carry no visualization defaults of their own, so this only overwrites what the user chose: a Spectrum-window mode or vis_classic profile picked in Classic is lost at the next launch. PR #531 exempted only the main-window mode (`includesMainWindowMode: false`). The defaults are already written where they belong: on a reset (`VisualizationPreferences.reset`) and on entering Classic (`prepareUIRuntime`). Before deleting the skin-load write, check what each key falls back to when it was never written (fresh install), and seed once on first launch if a fallback differs from Classic's default. Deleting the write also removes the `includesMainWindowMode` flag and the W214 family gate `appliesClassicVisualizationDefaults` (its `WMPClassicVisualizationDefaultsTests` pins go or change with it). **Done when** a Spectrum-window mode and a vis_classic profile picked in Classic survive a relaunch and a Classic skin pick, a reset still restores vis_classic / Purple Neon, and a fresh install still opens on Classic's defaults. Skills: `main-window-visualization`, `spectrum-analyzer-window`, `app-state`. |
| M39 | Give Classic its own main-window visualizer mode key | Classic and Original share `mainWindowVisMode`. `ModernMainWindowView` writes it alongside its own `modernMainWindowVisMode` on every mode change, and the key doubles as the command channel: the context menu (`MenuActions.setMainVisMode`) writes only it, both main-window views read it in `mainVisSettingsChanged`, and `ModernSkinEngine` and `VisualizationPreferences` write both keys. Classic can't tell its own choice from Original's, so entering Classic (`prepareUIRuntime`) overwrites it with Spectrum, and a mode picked in Classic is lost after a trip through Original. Split the key so each family persists its own mode, and route the menu's change through whichever family is running. **Done when** Classic's main-window mode survives Classic → Original → Classic, Original's survives the reverse, the menu checkmark is right in both, and the Spectrum overwrite on entering Classic is deleted. Skills: `main-window-visualization`, `app-state`, `original-skin-guide`. |

## EQ profiles — review follow-ups

From the code review of `feat/eq-profiles`, before it ships. Profiles and assignments are in SQLite
(`eq_profiles.db`); M41 builds on that. Skills: `audio-system` (EQ profiles), `app-state` (persistence).

| ID | Item | Notes |
|---|---|---|
| M41 | Split `EQProfileStore` into storage and presentation | The store also derives assignment keys (the `Track` extension), caches the queue marker (`appliesCache`) and formats UI text (`rowMarker`, `rowPrefix`, `setting`, `fileInfoLine`). The store should only read and write profiles and assignments; resolution and the strings move to a resolver/presenter beside it, and the tests use an in-memory database. **Done when** `EQProfileStore` holds no UI strings and no `Track` key logic, and every caller still reads the same. |
| M42 | Prune assignments whose track no longer exists | A local track's key is its file path, so a moved or renamed file leaves its track assignment behind, and nothing ever removes one. They accumulate forever and keep resolving if a different file lands at the old path. It is a query against `eq_profile_assignments`: drop local track-level rows whose file is gone, at launch or on a library scan. Decide first whether keying local tracks by library id instead of path is worth it (a moved file would keep its profile). **Done when** an assignment for a deleted local file is gone after the next launch or scan, and server, radio and YouTube rows are untouched. |
| M43 | Put the queue-row EQ marker in one place | The `∿` prefix is added separately in seven drawing paths: `PlaylistView` (twice), `ModernPlaylistView` (twice), `WMPPlaylistSurfaceView`, `WasabiSceneRenderer`, and `WinampModernComponentBridge`. One queue-row title helper (or a field on the row model each family already builds) should carry it, so a new playlist surface can't forget it and the marker's format lives in one place. **Done when** the marker is decided in one function and every playlist surface draws it unchanged in Classic, Original, `.wal` and `.wmz`. |
| M44 | WMP playlist widget: take the marker from the row, not the queue by index | `WMPPlaylistSurfaceView.draw` reads `audioEngine.playlist` and assumes row *i* is queue track *i*, guarded only by `libraryRows == nil`. If the widget's rows ever differ from the queue, the marker lands on the wrong track. Carry `hasEQProfile` on the row model the way the `.wal` path does (`WinampModernPlaylistRow.hasEQProfile`); fold into M43 if that lands first. **Done when** the widget no longer reads the engine's playlist to draw. |
