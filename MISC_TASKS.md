# Miscellaneous — open backlog

Open rows that belong to no skin-subsystem backlog. Read the owning skill before picking one up.

|---|---|---|
| M21 | Playlist rows mark a video with a `[V] ` text prefix instead of the YouTube rows' video / music glyphs | The Library Browser's YouTube rows mark each form on disk with a text glyph that takes the row's text color: `♫` for audio, `▶\u{FE0E}` for video (`YouTubeMediaKind.rowMarker`, `YouTube/YouTubeRows.swift` ~L102). The playlist spells the same fact as `"[V] "`, built four times by hand: `Windows/Playlist/PlaylistView.swift` ~L339 and ~L780 (Classic), `Windows/ModernPlaylist/ModernPlaylistView.swift` ~L233 and ~L497 (Original/Metal). **Direction:** one marker per `Track.MediaType`, shared by the YouTube rows and the playlist (move `rowMarker` off the `private` extension to a home both can reach), and the four playlist sites read it instead of `"[V] "`. **Decide first:** does every audio row get `♫`, only rows whose origin also has a video (`isYouTubeOrigin`), or none (video keeps its glyph alone)? Marking every audio row puts a glyph on almost the whole list. Check that both glyphs draw in a Classic skin's bitmap playlist font (a skin font with no `♫` / `▶` drops or substitutes it) and at both UI sizes. `.wal` and `.wmz` playlists show no video marker today; say whether they join. Skills: `ui-guide`, `youtube-source`. |
| M23 | A queued server video plays with less than the same film started from its row | Double-click on a movie or episode row calls `WindowManager.playMovie` / `playEpisode` / `playJellyfinMovie` … → `play(movie:)` / `play(episode:)` / `play(jellyfinMovie:)` …. A video that reaches the window through the playlist (`playVideoTrack`) instead calls `play(plexTrack:)` / `play(jellyfinTrack:)` / `play(embyTrack:)` (`VideoPlayerWindowController`), which is the path every library-menu verb takes (M15). Server reporting already matches: the track path starts each reporter from the track's id and reports a queued episode as an episode. Two differences remain. (1) **Plex external subtitles:** only the row path calls `videoPlayerView.setPlexStreams`. Check first whether a browser row's `PlexMovie` / `PlexEpisode` even carries streams: Plex's library listings and season `/children` usually omit `Stream` elements, which only `/library/metadata/<id>` returns, so the row path may pass an empty list too. (2) **Casting:** while a video cast runs, `playVideoTrack` casts the track's URL (`castVideoURL`), where the row entry points cast the server item (`castPlexMovie`, `castJellyfinEpisode` …). Compare what each sends to the device. **Direction:** once both match, double-click on a video row can run `TrackVerb.play` like a music row, and the six `WindowManager.play…` entry points, the browsers' `playMovie` / `playEpisode` wrappers and the video arms of both `handleDoubleClick`s go away. That also changes double-click to add the film to the playlist, so decide that first. Check against M17, which reshapes the same `play(…)` methods. Skills: `video-playback`, `plex-integration`, `jellyfin-integration`, `emby-integration`, `chromecast-casting`. |
| M24 | The CLI ignores `--cast` for a radio station | `nullplayer --cli --source radio --station "…" --cast "<room>" --cast-type sonos` plays the station locally and never casts: no discovery, no `castTrack` in the log. `CLISourceResolver` returns `.radioStation` (RadioManager is already playing), and `CLIMode`'s `.radioStation` case only calls `cliPlayer.monitorRadio()`. `CLIPlayer.setupCasting` (private) is reached only from `play(tracks:)`. The `cli` skill documents this exact command (`--source radio --station "KEXP" --cast "Living Room" --cast-type sonos`). Measured 2026-10-08 on the debug build: a one-line temporary call to `setupCasting` from `monitorRadio` cast Radio Paradise to "gym 2" correctly (local stop with `reason: userAction`, no reconnect, Sonos `PLAYING` for 30 s), so the cast machinery works and only the dispatch is missing. **Direction:** start casting from the one place both results pass through, not with a second copy of the `options.cast` check in `monitorRadio`. **Check at the same time:** quitting a CLI audio cast leaves the speaker playing. Ctrl-C exits through `exitAndRestoreTerminal` with no stop (the speaker still read `PLAYING` afterwards), and `quit()` stops only a video cast; its `audioEngine.stop()` sends the device stop from a `Task` that the immediate exit cuts off. Check the same for a non-radio audio cast (`--source plex --album … --cast …`). Skills: `cli`, `sonos-casting`, `radio-streaming`. |
| M25 | A film that fails to open leaves a black window and a paused engine, with no message | Measured 2026-10-08 on the debug build (Classic aquamp; local library film `short-film`, whose file is gone, played from the playlist after Radio Paradise, and again after a local song): the film window opens and stays black at 0:00, the main window shows pause, and the engine stays `paused` (checked 11 s later). The log has `VideoPlayerView: Playing short-film …` then `VideoPlayerView: Stopped` twice and nothing else: no error, no advance, no close. **Cause (read, not instrumented):** `VideoPlayerView.mediaPlayerStateChanged` handles `.stopped` and `.error` identically (`isActivelyPlaying = false`, `onPlaybackStateChanged?(false)`); neither reports a failure, and only `.paused` at end of media drives `reportPlaybackFinished`. A start that never plays is indistinguishable from a user stop. The engine was paused by `videoPlaybackDidStart`, which runs when the film is handed over, not when it starts playing. A film that played to its end and advanced into the broken one left the engine `stopped` and the same black window. **Decide first:** what a failed film should do: skip to the next row as a bad audio file does (`containingFolderIsPresent` rules: skip a bad file, stop on a vanished folder), or stop and say so. **Done when** a missing or unreadable film, in the playlist and from a browser row, is reported and the engine and window match whatever was decided. Check a missing local file, an unreadable one (non-video bytes in an `.mp4`) and an unreachable server film. Skills: `video-playback`, `audio-system`. |
| M26 | A playlist film shows the previous track's elapsed time, frozen | Measured 2026-10-08 on the debug build (Classic aquamp): playing a film row after Radio Paradise showed `00:05` in the main window with the film's title, and after an Audio Two song `00:06`; the snapshot read `time=5.4` while `2-video` played. **Cause (read):** `loadTrack`'s video branch sets `_currentTime = 0` but leaves `playbackStartDate` from the outgoing track, and the engine is still `.playing`, so `currentTime` returns the old track's elapsed time; `WindowManager.videoPlaybackDidStart` then calls `pause()`, which stores that as `_currentTime` and freezes it. **Direction:** the video branch is the one seam: leave the engine's clock at 0 when it hands a film over (`playbackStartDate = nil` beside `_currentTime = 0`), or route the main window's clock to the film while one plays. Check what the main window should show during a film first; `WindowManager.videoPlaybackState` may already own that for some skins. Every family's main window. Skills: `video-playback`, `audio-system`. |
| M27 | The playlist's Add File and Add Folder panels offer video files, then drop them | The Classic playlist's Add File panel (`PlaylistView.addFiles`, and the `miniOpen` button) allows `[.audio, .movie]`, and Add Folder discovers video (`LocalFileDiscovery.discoverMediaURLsAsync(…, includeVideo: true)`), but both hand the URLs to `AudioEngine.loadFiles`, whose `AudioFileValidator.quickValidate` accepts only `supportedExtensions` (audio): an `.mp4` is rejected as "Unsupported format" and never reaches the playlist. Load Playlist (`.m3u`) drops video entries the same way. Dropping the same file on the playlist works: `performDragOperation` appends `Track(url:)` directly. Found 2026-10-08 by reading the code while setting up a playlist film; not run. Original (`ModernPlaylistView`) and `.wal` (`WinampModernHostActionMenus`) call `loadFiles` too. **Direction:** decide in one place whether `loadFiles` takes video. `Track(lightweightURL:)` already sets `mediaType` from the extension, so `quickValidate` admitting `supportedVideoExtensions` would let every caller through; check that `loadTracks` → `loadTrack` routes the first row to the window when it is a film. **Done when** a video added through each panel lands in the playlist and plays in the video window, in every family that offers the panel. Skills: `video-playback`, `ui-guide`. |
| M29 | A queued server film is played through three copies of one `play(…Track:)` method, picked by a four-way id check | `VideoPlayerWindowController.play(plexTrack:)`, `play(jellyfinTrack:)` and `play(embyTrack:)` have the same body: read the server id off the `Track` (falling back to `play(url:)` without one), `endPreviousVideo()`, `startVideo(LoadedVideo(source: .…Item, queuedTrack:))`, then the server reporter's `videoTrackDidStart`. `WindowManager.playVideoTrack` picks one with `if plexRatingKey … else if jellyfinId … else if embyId … else play(url:)`. The three `videoTrackDidStart` signatures match apart from the id label (`ratingKey:` / `itemId:`). **Direction:** a `LoadedVideo.Source(queuedTrack:)` that reads the id off the track (`.plexItem` / `.jellyfinItem` / `.embyItem`, else `.localFile` / `.stream`), a start report on `LoadedVideo` beside `reporter`, and one `play(track:)`; the three methods and the `WindowManager` dispatch go. Only Plex passes `streamingHeaders`. Pure refactor: no report, scrobble or log line may change. Check by queuing a Plex, a Jellyfin and an Emby film plus a local one (Option+Enter, then Play) and comparing the reporter lines before and after. Skills: `video-playback` (*Server progress reporting*). |
| M33 | A film parked in a skin keeps key focus after a fullscreen round trip, so the skin's own key handlers stop hearing keys | A parked video window never becomes key (`VideoPlayerWindow.canBecomeKey` is false while parked), but F on a parked film unparks it and makes the free window key for fullscreen (`enterFullScreenReclaimingOutput` → `reclaimVideoOutput(reveal: true)`), and re-parking after Esc (`windowDidExitFullScreen` → `WMPVideoSurface.update` / `hostVideoOutputInWinampModernSkin` → `hostOutputWindow`) leaves it key: `canBecomeKey` turning false later resigns nothing. Measured 2026-10-08 on the debug build (Cablemusic and `211786-Cpro_Winamp_Modern`, Emby `Airplane!`): after F then Esc, Esc logged `VideoPlayer keyDown` from the film window's own monitor, not through the skin. The video keys still work, but a skin's own `keydown` / `System.onKeyDown` handlers and its focus ring get nothing until the skin window is clicked. Esc used to stop the film from this state; that is fixed by always consuming Esc in `handleVideoKey` (M18). **Direction:** in `hostOutputWindow`, when the video window is key, hand key back to its new parent (`parent.makeKey()`), so re-parking restores the rule that a parked window never holds focus. **Done when** after F then Esc on a parked film, `AXFocusedWindow` is the skin window and a key the skin authors a handler for reaches it, in `.wmz` and `.wal` (a tab and a video window of its own). Skills: `video-playback`. |
| M34 | Two Left presses while a film is paused move it back 10 s, not 20 s | `VideoPlayerView.skipBackward` / `skipForward` compute the target from `mediaPlayer.time`, which VLC does not advance while paused until the seek lands, so a second press before that seeks from the same old time. Measured 2026-10-08 on the debug build (Cablemusic, Emby `Airplane!`): paused at 26.01 s, Left, Left 0.5 s apart, resume and pause read 16.63 s; a single Right from 15.38 s read 26.01 s. Every mode, free or parked. **Direction:** keep the last requested target while a seek is pending (or while paused) and step from it, falling back to `mediaPlayer.time` once playback reports a new time. **Done when** two Left presses while paused read about 20 s back on the next pause timestamp, and a single press while playing still moves 10 s. Skills: `video-playback`. |
